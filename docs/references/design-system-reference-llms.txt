# Design System Reference (LLM-friendly)

Every widget shipped in `lib/design_system/`, in one file. Read this before
composing a screen: `tool/ui_lint.dart` fails a screen that hand-rolls a
control the kit already owns, and this is where you find out what it owns.

## How to use this file

- **Start with `Use when:` / `Instead:`.** Picking the wrong control is the
  failure no gate catches — `ui_lint` checks that a widget came from the kit,
  never that it suited the job. `Instead:` names the neighbour that gets
  reached for by mistake and the question that separates the two.
- **Reach for a component by name; do not hand-roll it.** Everything here is
  exported from `lib/design_system/design_system.dart`, so one import gets you
  all of it.
- **Colour, radius, motion, depth and type are tokens**, from `lib/theme/`.
  A component takes its own defaults from them; passing a literal in is what
  `ui_lint` rules 11–18 fail.
- **`Enums`** are the variant sets. They are the only legal values for the
  matching parameter — there is no string-typed variant anywhere in the kit.
- **`Also in this file`** lists the companion classes exported alongside the
  main one: the item types, the controllers, the slot widgets.
- **`Tier`** is the layer the component sits on, and therefore what it may be
  built from. `foundation` declares nothing that paints — the style chain, the
  scopes, the press and inset plumbing. An `atom` is the smallest thing that
  paints and reaches no further than another atom. A `molecule` composes
  atoms into one unit of meaning; an `organism` composes molecules into a
  region of a screen; a `template` composes organisms and owns nothing but
  layout. An import may reach its own tier or below and no further, which
  `tool/ui_lint.dart` fails a build over.

Generated by `tool/design_system_reference.dart` — do not hand-edit. Run
`make design-system-reference-update` after adding a component. Selection
guidance is curated in that file, and a component with no entry fails
`make check`.

### `DSComponentStyle`

### `DSText`

- **Use when:** Every string the app draws. Pass the `DSTextRole` that says what the string is — `pageTitle`, `eyebrow`, `itemTitle`, `itemMeta`, `fieldError`, `metric`, `control`, `count` and thirteen more — and the step, the grey, the weight, the tracking, the casing, the line limit, the ellipsis, the tabular figures, the text-scale ceiling and the heading semantics all arrive with it. `DSText.rich` with `DSTextSpan` for a line whose runs differ, so an emphasised word does not have to leave the system.
- **Instead:** A raw `Text` with `Theme.of(context).textTheme.x.copyWith(...)` — that is this decision re-made per call site, and it is what left twenty-one places clipping with no ellipsis and three `semanticsLabel`s across two hundred and thirty-seven strings. The question that separates the roles is what the string *is*, never how big it looks: a row's supporting line is `itemSubtitle` and a field's is `fieldHelper`, and they are the same size today only because the scale currently puts them there. A one-off that no role fits is `style: DSTextStyle(...)` at layer 4, not a new role.

## Action (4)

### `DSButton`

- **Use when:** A tap causes something to happen — submit, confirm, run, open. Five variants, one meaning each: `primary` (the one action this screen is for, at most one per view), `secondary` (a real action that is not the main one), `outlined` (secondary weight where a fill would compete with the content behind it), `ghost` (available but must not draw the eye — Cancel, Skip, Show more) and `destructive` (removes something the user cannot get back).
- **Instead:** `DSIconButton` when the icon alone carries the meaning and there is no room for a label — there is no `isIconOnly` here, because a label-less button skips the tooltip and the semantic label a `DSIconButton` requires. `DSFab` for the one screen-level action that floats above the content. `DSCard(onTap:)` where a button that looks like a card was wanted. For a green, amber or blue button, no variant: `style: DSButtonStyle(fillColor:, labelColor:)` at whichever layer suits — a green "Retry" is still a secondary action, and a status usually belongs on a `DSMessage` rather than on a button.

### `DSIconButton`

- **Use when:** An action with no label, where the glyph is unambiguous AND space genuinely does not allow one — an app bar, a card corner, a list trailing slot. Two variants: `standard` for an action that must be available without competing with the content, `filled` for the one prominent icon action on a surface. `semanticLabel` is required and the tooltip defaults to it; `tone` carries meaning; a toggle passes `selectedIcon` so the fill is not the only signal; `DSIconButtonGroup` keeps the targets 8dp apart.
- **Instead:** A labelled `DSButton` in a form or a pinned action bar, always — an icon that needs its tooltip to be understood in a primary action position is a design smell. The set a reader knows unlabelled is small: search, home, close, share, add, delete, settings. `DSMenu` when there are more than two of them in one slot. A tonal or outlined icon button is `DSIconButtonStyle` in `ThemeData`, set once, not a variant passed at every call site.
