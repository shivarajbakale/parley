Ask Parley

A screen-aware agent that lives on the orb, speaks three verbs, and taps nothing.

parley-a07 · priority 15 · area native · status not_started · sources: parley-a07.feature-plan.json, docs/plans/agent.md

01Verdict

The idea is good and the infrastructure is already paid for. The first draft of the confirmation design was wrong, and this is the corrected one.

Why it fits Parley

The accessibility service already holds the exact node tree of the foreground window — real text, real bounds, real class names, no OCR. It also already has a model client and an injector. Nothing here is a new subsystem; it is a new orb mode wired to things that exist.

What is genuinely new

Turning a node tree into something a model can read well, and building the refusal layer. Everything else is plumbing. The first of those is where the tests go.

The positioning, in one line

Gemini and Assistant can see your screen. Parley can read it and act in it. That is the difference worth building: exact structure instead of pixels, and a loop that ends in the app instead of in a chat window.

02Problem

Parley speaks for you and cannot answer for you or act for you.

Everything it knows is what you just said, and the one thing it can change is a text field. So a screen that needs reading, or a task that needs three taps, is a screen Parley can only help you type into. The service is already holding the answer and the model is already holding the question — nothing connects the two.

03What changed, and why

The first draft put a per-step confirm loop on a phone. That was a desktop pattern on a mobile device and it contradicted the product's own premise.

was
A snap-sheet with four buttons

Run this step · Run all read-only · Stop · Insert the answer, tapped in sequence while the app underneath competed for the same pixels. One-handed, in a hurry, in a chat app.

now
The orb is the only control

Hold to ask. Hold to commit. Hold longer to send. Zero buttons on the main path. The plan is read while the finger is still down, which is the one moment a mobile confirmation belongs in.

was
The orb goes inert while a run is live

Because the agent can click any node it can name, and the orb is a node — so it was switched off to the person as well as to the model.

now
Inert to the agent, live to the person

The orb is the brake. You are already holding the phone to watch a run; your thumb is on it. Touching it stops the run after the current step.

kept
Refusals stay local, pure, and tested

Unchanged. Step class, allowlist, budgets, orb overlap — none of these are the model's decision and none of them need a device.

kept
Irreversible is the safe default

Still graded up, still on its own, still saying it cannot be undone. It just asks for a longer hold instead of a dialog.

kept
Taps exist, as the second language

Real tap equivalents for every hold, plus the settings page. TalkBack and switch control both make a sustained hold genuinely hard, and a product built on an accessibility service that excludes its own users has failed at the premise.

04The orb, and its new mode

The orb already speaks three gestures. Ask mode is added beside them, never on top of them.

Why a mode and not a fourth gesture

Hold dictates. Double-tap-hold edits. Volume tap-tap-hold dictates. A fourth hold-like gesture would be unlearnable and would collide with two that already work. A toggle is a state the sphere can show, not a timing window the user has to remember.

05Hold to ask

Nothing new. The existing listening capsule, in the existing mode.

The agent reuses the MiniMax key that voice edit already uses. No key means it refuses before the mic opens, with the same wording voice edit already has — not after it records.

06Hold to commit

The plan arrives in the capsule and the user is still holding. Release runs it.

A run that needs more than five steps ends as over budget rather than wandering. A task that long is two confirmed runs.

07Running · the orb is the brake

The stop control is where the hand already is.

The rule that changed

The orb must be inert to the agent and live to the person. Any step whose target bounds overlap the orb's own window is refused by AgentPolicy — before the model is even asked. So the agent cannot aim at the orb, and the user can.

08The third hold

This is the one place a hold genuinely isn't enough friction. So it asks for a longer one, and says why out loud.

Read

read  Reading, scrolling, looking. Runs on the commit hold. Nothing to undo.

Write  /  irreversible

write send  Write runs on the commit hold. Send stops the run and asks for a third.

Classification is local and the model has no vote. A click whose target matches a send or commit pattern grades up to irreversible, because being wrong about that costs one extra tap rather than one sent message. One irreversible step per run, never batched with anything else.

09Readout, not control surface

A phone can carry a line and a log. It cannot carry a control surface over a live app.

What stays on the orb

One line, near the thumb, hold-aware. The plan in words. The current step. The answer. Nothing scrollable, nothing tappable on the main path.

What moves to History

The full plan, every step and its outcome, and the exact context that was sent. Scrollable, copyable, and the place a question actually gets reviewed.

The sheet survives as a readout only. It is not a sheet any more — it is the listening capsule, widened.

10ScreenContextSerializer

The feature, not a formatting helper. A node tree is a bad prompt: deep, duplicated, full of invisible containers.

Never sent

Password fields, anything marked a secret, and the focused text of a browser's address bar. sendScreenContents covers the rest, and the character count of what is actually going is on the orb before it goes.

An agent that silently answered from half a screen is worse than one that declines — so truncation is a visible state, not a silent one.

11AgentPolicy · every refusal

Pure functions over a step and a config. No device, no network, all of it unit-testable.

12Revalidation

The reason ids are re-derivable from the path rather than random.

The single most important test in the feature

A hallucinated step that gets dropped is a non-event. One that gets clicked ends the product. Steps naming a node that is not on screen are dropped and shown struck through in the transcript — because a silently dropped step is a plan that lied.

13The closed action set

Six verbs, and the whole reason a user can read what an agent can do on one screen.

ActionClassNotes
answerreadNo acting. A question returns to the capsule and, if asked, into the focused field.
clickwrite sendGrades up to irreversible on a send/commit pattern. Reuses Injector for fields.
setTextwriteReuses the existing TextSplicer — hint text, selection, leading space, surrogate pairs, all already tested.
scrollreadThe one navigation that is not a step backwards.
waitreadCapped. An agent that has to wait three times is an agent that guessed wrong.
backwriteGenuinely unsure this earns its place — see question Q6.

14Agent settings

The one place with rows and switches. It isn't a moment, it's a place.

The page leads with Send screen contents rather than with an explanation of what the agent is, because the person opening it is usually reacting to something it already did. A value that failed to load renders as a dash, never as Off — off is an answer, a failure is not one.

15Agent run transcript

Where the plan actually gets reviewed — because here there are no mis-taps.

It ends on What was sent, so the user can read exactly what left the phone and take it to a provider's dashboard if they need to. A run whose sending cannot be inspected is a run nobody should trust with a banking app.

19Open questions

These are the ones I actually do not know, and each of them changes the design rather than the wording.

Q1 · Is triple-tap the right activation at all?

Triple-tap is a timing window the user has to remember — which is exactly what I said Ask mode was avoiding. An alternative is a persistent ring the user turns on and off in settings, or a long-press on the docked side of the orb.

triple-tap (proposed)persistent in settingslong-pressask mode always on

Why it matters: this is the first thing anyone touches, and it decides whether the feature is discoverable at all.

Q2 · Does the plan need a detail view on the orb?

One line is honest and fast, but "3 steps · ends by emailing you" is a summary, and a user who disagrees with the summary has no way to check it before releasing.

one line only (proposed)one line, slide up for the stepsall steps always

Why it matters: it is the difference between a fast approval and an informed one.

Q3 · Should a run stop at the send, or complete the reads and hold there?

Currently: the run finishes everything reversible, then stops and asks for the third hold. The alternative is to stop the moment a send is planned, before any of it happens.

finish reads, hold at the sendstop at the first send

Why it matters: the first is more useful and does more before the user can stop it.

Q4 · Is the allowlist right, or should it prompt?

An allowlist means a new app is unreadable until chosen. That is the safe default and it is also friction on the second use, which is where people usually decide whether they keep a tool.

allowlist (proposed)denylist + a once-per-app promptallowlist with a one-tap add

Why it matters: it is the difference between one session of friction and a permanently quiet feature.

Q5 · Should the question half ship before the acting half?

"What does this error mean" needs no permissions, no refusals, no undo and no allowlist. It is most of the value at none of the risk. The acting half is what makes this plan heavy.

agent that acts (proposed)answer-only first, acting later

Why it matters: the acting half is roughly five times the work and all of the danger. The question half is roughly the serializer.

Q6 · Does back earn a place in the action set?

A plan that navigates backwards is a plan that misread the screen, and the revalidation refusal already handles the case where it belongs.

drop itkeep it (proposed)

Why it matters: it is the one verb in the set whose purpose is to recover from the agent's own mistakes.

Q7 · Should History keep agent runs at all?

The transcript is where the plan gets reviewed and where "what did you send" gets answered. But it is also a record of every screen the agent read, which is a different kind of sensitive history than dictations.

keep, with a retention settingkeep, forever (proposed)ephemeral — nothing retained

Why it matters: the app already stores a history; this is the first thing in it that was not something the user typed.
